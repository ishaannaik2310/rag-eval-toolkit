# Project 1: Open-Source RAG Eval & Observability Toolkit ("Pytest for RAG")
## Complete System Specification & Architecture Design

---

## 1. Executive Summary & Vision

The **RAG Eval & Observability Toolkit** (`rag-eval`) is a developer-first, lightweight, modular testing framework designed to evaluate, benchmark, and assert the quality of Retrieval-Augmented Generation (RAG) pipelines. Functioning as a **"Pytest for RAG"**, `rag-eval` brings deterministic testing, LLM-as-a-judge evaluations, and CI/CD quality gates to modern AI applications.

### Core Value Propositions
- **Declarative Test Specifications**: Define evaluation datasets in YAML, JSON, or Python code.
- **RAG Triad & Custom Metrics**: Built-in support for Context Precision (MAP@K), Context Recall, Faithfulness (Hallucination detection), Answer Relevance, and Semantic Similarity.
- **Pluggable LLM Judges**: Seamless integration with OpenAI, Anthropic, Ollama, and custom HTTP endpoints without vendor lock-in.
- **Rich CLI & Reporting**: Beautiful terminal UI with progress bars, failure diagnostics, tabular summaries, and machine-readable exports (JUnit XML, JSON, Markdown).
- **CI/CD Quality Gates**: Exit codes and threshold assertions for GitHub Actions, GitLab CI, and automated deployment pipelines.

## 3. Core Data Models (Pydantic v2)

All data structures are strongly typed using Pydantic v2:

1. **`Chunk`**: Represents a retrieved unit of context.
   - `id`: Optional unique identifier.
   - `text`: Raw textual content of the chunk.
   - `metadata`: Arbitrary dictionary of metadata (e.g., document source, page, timestamp).
   - `score`: Optional retrieval similarity score from the vector database.
   - `is_relevant`: Optional ground-truth boolean flag for deterministic precision benchmarks.

2. **`TestCase`**: Represents a single evaluation sample.
   - `id`: Unique test case identifier.
   - `query`: The user input or prompt.
   - `contexts`: List of retrieved contexts (`list[Chunk]` or `list[str]`).
   - `expected_output`: Optional reference answer (ground truth).
   - `actual_output`: The response generated by the RAG system under test.
   - `metadata`: Optional test case metadata (tags, category, domain).

3. **`EvalSet`**: A collection of test cases.
   - `name`: Name of the evaluation suite.
   - `description`: Optional suite description.
   - `test_cases`: List of `TestCase` objects.

4. **`MetricResult`**: Output of an individual metric evaluation.
   - `name`: Metric identifier (e.g., `context_precision`, `faithfulness`).
   - `score`: Normalized score between `0.0` and `1.0`.
   - `reason`: Detailed natural language explanation or calculation breakdown.
   - `threshold`: Configured passing threshold.
   - `passed`: Boolean indicating if `score >= threshold`.
   - `metadata`: Metric-specific execution details (tokens, latency, intermediate steps).

5. **`TestCaseResult`**: Aggregated evaluation result for one test case.
   - `test_case_id`: ID of the evaluated test case.
   - `query`: Query string.
   - `metric_results`: List of `MetricResult` objects.
   - `passed`: `True` if all metric assertions passed.
   - `execution_time_ms`: Total execution time in milliseconds.

6. **`EvalRunResult`**: Complete evaluation run report.
   - `eval_set_name`: Name of the evaluation set.
   - `test_case_results`: List of `TestCaseResult`.
   - `total_tests`: Total count of test cases.
   - `passed_tests`: Total count of passing test cases.
   - `failed_tests`: Total count of failing test cases.
   - `average_scores`: Mapping of metric names to mean scores.
   - `duration_seconds`: Total runtime duration.
   - `passed`: Overall suite pass/fail status.

## 4. Metrics Design

### 4.1 Context Precision (Rank-Weighted Retrieval Metric)
Measures whether the relevant retrieved chunks are ranked higher than irrelevant ones.
- **Formula (Mean Average Precision @ K)**:
  $$\text{Context Precision@K} = \frac{\sum_{k=1}^K (\text{Precision@k} \times v_k)}{\text{Total Relevant Chunks}}$$
  where $v_k \in \{0, 1\}$ is the relevance indicator for chunk at rank $k$, and $\text{Precision@k} = \frac{\text{Relevant Chunks in top } k}{k}$.
- **Modes**:
  1. *Deterministic*: Evaluated when `Chunk.is_relevant` is explicitly provided in the test case dataset.
  2. *LLM-Assisted*: When ground truth relevance is not annotated, an LLM judge evaluates each retrieved chunk against the query / reference answer to determine relevance.

### 4.2 Faithfulness (Hallucination Detection)
Evaluates whether the claims made in `actual_output` are strictly supported by the retrieved `contexts`.
- **Process**:
  1. Extract atomic factual claims from `actual_output`.
  2. For each claim, check if it can be directly inferred from the retrieved contexts.
  3. $\text{Faithfulness Score} = \frac{|\text{Supported Claims}|}{|\text{Total Claims}|}$.

### 4.3 Answer Relevance
Evaluates whether `actual_output` directly addresses the user's `query` without straying off-topic or including redundant fluff.
- Uses LLM judge or embedding cosine similarity between the generated question variations and original query.

## 5. LLM Judge Architecture

To avoid heavy third-party SDK bloat, judges communicate directly over HTTP using `httpx`:
- **`BaseJudge`**: Abstract interface with `async def generate(prompt, system_prompt, json_mode) -> str`.
- **`OpenAIJudge`**: Direct integration with `/v1/chat/completions` supporting `gpt-4o`, `gpt-4o-mini`, etc.
- **`AnthropicJudge`**: Direct integration with `/v1/messages` supporting `claude-3-5-sonnet`, `claude-3-haiku`, etc.
- **`LocalJudge`**: Direct integration with Ollama or vLLM OpenAI-compatible endpoints (`http://localhost:11434/v1`).

## 6. Test Runner & CLI

### CLI Interface (`rag-eval`)
- `rag-eval run <path/to/eval.yaml>`: Executes evaluation suite and displays Rich tables.
  - Flags: `--judge openai:gpt-4o-mini`, `--concurrency 5`, `--output-json results.json`, `--fail-under 0.85`
- `rag-eval init`: Generates a starter `evals/eval_sample.yaml` dataset.
- `rag-eval check <path/to/eval.yaml>`: Validates dataset syntax and structure without invoking LLMs.

### Exit Codes for CI/CD
- `0`: All tests passed their configured thresholds.
- `1`: One or more tests failed metric thresholds.
- `2`: Configuration or runtime error (invalid YAML, network failure, missing API keys).
